# PRD-<slug> — <Product / Feature Name>

<!-- Tip: use a short kebab-case slug (≤ 5 words), e.g. `library-book-tracker` — it must match the filename -->

## 1. Vision

<!-- Tip: 2–3 sentences answering "12 months from now, whose life does this system change and how" — no jargon -->

Let library members borrow and return books 3× faster, and give librarians a real-time view of every book's status without checking several systems.

## 2. Problem

<!-- Tip: who hits what problem, how they work around it today, why it hurts -->

Librarians spend an average of 4 minutes per book on checkout because they have to verify the member, verify the book, record in/out in Excel, and confirm with a paper signature. Members complain about long queues an average of 12 times per week, and Excel hits conflicts when several people edit at once 1–2 times per day.

## 3. Personas

<!-- Tip: 2–4 personas is enough; each has a role + context + specific pain -->

- **Member** — a general user who borrows 2–5 books per month, wants to know which books are available/reservable, and wants fast borrow-and-return
- **Librarian** — front-counter staff who wants a single tool covering checkout/checkin/search/audit
- **Admin** — the head librarian, who wants a loan statistics dashboard plus catalog and user-permission management

## 4. Goals

<!-- Tip: write these as outcomes the user gets (not a feature list); 3–6 items -->

- Cut average checkout time to ≤ 90 seconds per book
- Let members search, reserve, and check book status online 24/7
- Let librarians see the overdue list and send reminders from one screen
- Let admins export the monthly loan report in one click

## 5. Non-goals

<!-- Tip: state clearly what is "out of scope here" to prevent scope creep — you may point to a future phase -->

- Online fine payment (phase 2)
- Mobile app (phase 2 — responsive web is enough for the first version)
- Reading e-books inside the system (not in scope)
- Integration with the university accounting system (to be considered later)

## 6. Success Metrics (SC-###)

<!-- Tip: every SC must be **measurable** + **technology-agnostic** + state how it is measured — spec-kit pattern -->

- **SC-001** — a member checkout completes in ≤ 90 seconds (p95), measured from the server log + UI tracking
- **SC-002** — supports 200 concurrent users with response p95 ≤ 800 ms (load test)
- **SC-003** — 95% of checkouts succeed on the first press with no retry (UX funnel)
- **SC-004** — long-queue complaints drop ≥ 60% in the first 3 months after launch (survey + ticket count)
- **SC-005** — a librarian produces the weekly overdue report in one click within 5 seconds (manual test)

## 7. User Stories Overview (Prioritized)

<!-- Tip: every story must be **Independently Testable** (ship that one story and a user can actually use it) -->
<!-- Given/When/Then acceptance detail lives in the SRS / FEAT (FR-###) -->

### US1 — Member checks out a book (Priority: P1) — MVP

**As a** Member **I want** to borrow a book through the librarian at the counter **so that** I can take the book home without a long wait

**Why this priority:** core revenue/value loop — if checkout does not work, the system is worth nothing

**Independent Test:** librarian logs in → scans the member barcode → scans the book barcode → presses confirm → the system records the loan and shows the due date — ship only this story and it is genuinely usable

---

### US2 — Member searches and checks book status (Priority: P2)

**As a** Member **I want** to search whether a book is in the system and whether it is available or on loan **so that** I can decide whether to travel to the library

**Why this priority:** cuts counter traffic and adds convenience — complements US1 but works on its own

**Independent Test:** open /search → type a book title → see results + status (available/borrowed/reserved) — this story alone is already useful standalone

---

### US3 — Librarian reviews overdue loans and sends reminders (Priority: P3)

**As a** Librarian **I want** to see the list of overdue books and send an email reminder **so that** the books come back before they are lost for good

**Why this priority:** reduces loss but is not a launch blocker — can follow P1/P2

**Independent Test:** librarian logs in → opens /overdue → sees the list → presses Send Reminder → the system emails the member → the action lands in the audit log

---

## 8. Constraints

<!-- Tip: deadline, budget, tech, compliance — the things that "must be followed" -->

- **Deadline**: launch the MVP within Q3 2026
- **Budget**: internal team only, no vendor
- **Tech stack**: Next.js + Postgres + Prisma (see `REF-TechStack.md`)
- **Compliance**: PDPA — member data stored in Thailand, 7-year retention
- **Language**: Thai (UI) + English (admin reports)

## 9. Assumptions

- Every member already has a registered email/mobile number
- The library already has a barcode scanner at the counter
- WiFi in the library is stable (no offline-first design needed for the MVP)

## 10. Risks

<!-- Tip: risk → mitigation; never leave a bare risk with no plan to handle it -->

- **R1** — Excel data migration comes out corrupted → mitigation: write a migration script + dry-run on staging + manual spot check of 100 records
- **R2** — Librarians resist the system change → mitigation: 2 training sessions + run Excel and the new system in parallel for 2 weeks
- **R3** — Search load higher than expected → mitigation: add a Postgres index + cache the top-100 queries in Redis

## 11. Glossary

<!-- Tip: use the same vocabulary across the whole project — SRS/FEAT/FN link back here -->

- **Member** — a library member (chosen over "patron"/"user")
- **Loan** — one borrowing of a book (a record in the DB)
- **Overdue** — a loan where `due_date < today` and `returned_at IS NULL`
- **Catalog** — every book in the system (book master)
- **Reserve** — a member books a currently-loaned title to get the next slot in the queue
