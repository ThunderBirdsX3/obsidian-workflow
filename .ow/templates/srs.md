# SRS-<slug> — <Product / Feature Name>

## 1. System Overview

<!-- Tip: 1 paragraph describing the system context — who uses it, what it does, what it connects to — no more than 5 lines -->

Library Book Tracker is a web application (Next.js + REST API) for a university library. It supports 3 user roles (Member, Librarian, Admin) and handles checkout/checkin/search/overdue management with Postgres as the single data store. The system talks to an external SMTP service to send email reminders, and to a barcode scanner (HID keyboard input) at the counter.

## 2. Scope

<!-- Tip: derive this from the PRD § Goals/Non-goals — but from the system's point of view, not the user outcome -->

**In scope:**
- Web UI (responsive, Thai)
- REST API (JSON, JWT auth)
- Email notification (SMTP)
- Postgres database + migrations

**Out of scope:**
- Mobile native app
- E-book reader
- Payment gateway
- Real-time push notification

### FR-001 — Member checks out a book

- **Priority**: P1
- **Source user story**: US1 (PRD-library-book-tracker)
- **Description**: the system must let a Librarian record a Member's loan of 1 Book in a single action, with default due_date = today + 14 calendar days
- **Inputs**: `member_id` (UUID), `book_id` (UUID), `librarian_id` (from the session)
- **Outputs**: `loan_id` (UUID) + `due_date` (ISO 8601)
- **Pre-conditions**:
  - the Member must be `status = active`
  - the Book must be `status = available`
  - the Member has fewer than 5 active loans (business rule)
- **Post-conditions**:
  - Loan record `status = open`
  - Book `status = borrowed`
  - an audit log entry is created
- **Acceptance** (Given/When/Then):
  1. **Given** the Member has 2 active loans + Book A is available, **When** the Librarian checks out Book A to the Member, **Then** the system creates the loan + shows due_date + flips Book A to borrowed
  2. **Given** the Member has 5 active loans, **When** the Librarian checks out Book A, **Then** the system rejects it with the error "loan limit exceeded"
  3. **Given** Book A has `status = borrowed`, **When** the Librarian checks out Book A, **Then** the system rejects it with the error "book not available"
- **Error handling**: 409 Conflict on a race condition (2 librarians checking out the same copy) — enforced by a DB unique constraint on `(book_id, status=open)`
- **Dependencies**: FR-010 (Auth), FR-020 (Catalog read), DB schema (book.status, loan)

### FR-002 — Member searches for a book

- **Priority**: P2
- **Source user story**: US2
- **Description**: the system must let a Member search books by keyword (title, author, ISBN) through a public endpoint without logging in
- **Inputs**: `q` (string, 1–100 chars), `page` (int, default 1), `limit` (int, default 20, max 50)
- **Outputs**: list of `{book_id, title, author, status, cover_url}` + total count + pagination
- **Pre-conditions**: no auth required
- **Post-conditions**: the search query is recorded in the analytics log (anonymous)
- **Acceptance**:
  1. **Given** the Member is not logged in, **When** GET `/api/search?q=harry`, **Then** the system returns the books whose title/author match "harry" + their current status
  2. **Given** no book is found, **When** searching `q=xyz`, **Then** return `{items: [], total: 0}` (HTTP 200), not a 404
  3. **Given** `q` length = 0, **When** searching, **Then** return HTTP 400 + the message "query required"
- **Error handling**: 400 validation, 500 on a DB error
- **Dependencies**: DB index `book(title gin_trgm, author gin_trgm)`

### FR-003 — Librarian views the overdue list

- **Priority**: P3
- **Source user story**: US3
- **Description**: the system must show the Librarian every loan where `due_date < today` and `returned_at IS NULL`, along with the member's contact info
- **Inputs**: `branch_id` (optional, defaults to the librarian's own), `sort` (default `due_date asc`)
- **Outputs**: list of `{loan_id, member_name, member_email, book_title, due_date, days_overdue}`
- **Pre-conditions**: the user must have the role `librarian` or `admin`
- **Post-conditions**: the view event is written to the audit log
- **Acceptance**:
  1. **Given** 3 loans are overdue, **When** the Librarian opens `/overdue`, **Then** they see 3 rows sorted by due_date, oldest first
  2. **Given** no loan is overdue, **When** they open `/overdue`, **Then** they see the empty state "No overdue books"
  3. **Given** a Member-role login, **When** they open `/overdue`, **Then** HTTP 403
- **Dependencies**: FR-010 (Auth + RBAC), FR-001 (loan record)

---

### FR-004 — Librarian sends an email reminder

- **Priority**: P3
- **Source user story**: US3
- **Description**: the system must send an email reminder to the member on an overdue loan, fired one member at a time from a single Librarian button press (no batching in the MVP)
- **Inputs**: `loan_id`
- **Outputs**: `reminder_id` + status `sent | failed`
- **Acceptance**:
  1. **Given** the loan is overdue + the member has an email, **When** the Librarian presses Send Reminder, **Then** the system sends the email + stores the reminder record + shows the toast "Sent successfully"
  2. **Given** an SMTP timeout, **When** Send Reminder is pressed, **Then** record `status=failed` + show the error + allow a retry
- **Dependencies**: FR-003, external SMTP, NFR-003 (email delivery)

---

### FR-010 — Authentication + RBAC

- **Priority**: P1 (foundational — blocks every story)
- **Source user story**: implicit (cross-cutting)
- **Description**: the system uses JWT-based auth + RBAC by role (`member`, `librarian`, `admin`); see `REF-AuthorizationMatrix.md`
- **Acceptance**:
  1. **Given** valid credentials, **When** POST `/api/auth/login`, **Then** the system returns a JWT (15 min) + a refresh token (7 days)
  2. **Given** an expired JWT, **When** calling a protected endpoint, **Then** HTTP 401 + the client refresh flow
  3. **Given** the member role, **When** calling an admin-only endpoint, **Then** HTTP 403
- **Dependencies**: NFR-002 (Security), `REF-AuthorizationMatrix.md`

## 4. Non-functional Requirements (NFR-###)

<!-- Tip: every NFR needs a measurable threshold — never a bare "fast" or "secure" -->

### NFR-001 — Performance

- **Threshold**: API p95 latency ≤ 800 ms (search), ≤ 500 ms (checkout) under 200 concurrent users
- **Measurement**: k6 load test + Datadog APM trace
- **Linked SC**: SC-002

### NFR-002 — Security

- **Threshold**:
  - passwords hashed with bcrypt cost ≥ 12
  - JWT signed with RS256 (asymmetric)
  - every write endpoint carries a CSRF token (for the web client)
  - PII (email, phone) encrypted at rest (Postgres pgcrypto)
- **Measurement**: `/ow-secure` pre-flight + an OWASP ZAP scan before launch

### NFR-003 — Reliability / Availability

- **Threshold**: 99.5% uptime (≤ 3.6 hours downtime/month)
- **Measurement**: uptime monitor (UptimeRobot) + monthly SLA report

### NFR-004 — Accessibility

- **Threshold**: WCAG 2.1 AA — contrast ≥ 4.5:1, keyboard navigation 100%, screen reader tested in NVDA + VoiceOver
- **Measurement**: axe-core CI check + the manual audit checklist `90-TestPlan/a11y-checklist.md`

### NFR-005 — i18n / Localization

- **Threshold**: UI 100% Thai, admin report English option; date format `dd/MM/yyyy` (Thai), `yyyy-MM-dd` (ISO in exports)
- **Measurement**: locale test + manual review

### NFR-006 — Data Retention (PDPA)

- **Threshold**: keep member PII for 7 years after last activity → then anonymize; audit log 5 years
- **Measurement**: cron job + quarterly audit
