# FEAT-<slug> — <Feature title>

<!-- Tip: a feature must be small enough to ship in 1 sprint (≤ 2 weeks); anything bigger → split into several FEATs -->

## 1. Goal

<!-- Tip: 1–2 sentences answering "what does this feature let the user do" — an outcome, not a task list -->

Let library members borrow a book through the Librarian at the counter within ≤ 90 seconds, with the system recording the loan + updating book status atomically + showing the due date immediately

## 2. Roles

<!-- Tip: who "does what" in this feature — link back to the Role doc -->

- **[[Role-Member]]** — sees their own loan history + due dates
- **[[Role-Librarian]]** — executes checkout, overrides edge cases (e.g. loan limit), sees their own audit trail
- **[[Role-Admin]]** — sees the system-wide audit + overrides business rules (manually)

## 3. User Stories (Prioritized)

<!-- Tip: pull these from the PRD § User Stories Overview, then add the Given/When/Then acceptance detail -->
<!-- Every story must be **Independently Testable** — implement just that story and it is genuinely usable -->

### US1 — Member checks out a book, basic path (Priority: P1) — MVP

**As a** Member **I want** to borrow a book through the Librarian at the counter **so that** I can take the book home

**Independent Test:**
1. Seed DB: 1 active member (0 active loans), 1 available book
2. Librarian logs in → scans the member barcode → scans the book barcode → presses confirm
3. Verify: the loan record is created, book status = borrowed, the UI shows due_date
4. Works standalone — no search/overdue/email needed first

**Acceptance Criteria (Given/When/Then):**

1. **Given** the Member has 2 active loans + Book A is available, **When** the Librarian checks out Book A to the Member, **Then** the loan record is created + Book A → borrowed + the UI shows due_date = today + 14 days
2. **Given** the Member has 5 active loans, **When** the Librarian presses checkout, **Then** the system rejects it + shows the error "Loan limit exceeded (max 5)"
3. **Given** Book A has `status = borrowed`, **When** the Librarian scans Book A, **Then** the system rejects it + suggests "This copy is on loan — view the reservation queue?"
4. **Given** a DB error occurs mid-checkout, **When** confirm is pressed, **Then** no loan record is created (rollback) + an error is shown + a retry is offered

**FR refs covered:** FR-001, FR-010 (auth)
**Function refs:** [[FN-Web-Lib-Checkout]], [[FN-API-Loan-Create]]
**DS components used:** `Button`, `Input`, `Toast`, `Modal` (confirm)
**Risks:** race condition (2 librarians → the same copy) → use a DB unique constraint

### US2 — Member views their own loan history + due dates (Priority: P2)

**As a** Member **I want** to see my current loans + my history **so that** I know when a book has to go back

**Independent Test:** member logs in → opens `/my-loans` → sees the active loan list + history (paginated)

**Acceptance Criteria:**

1. **Given** the Member has 2 active loans + 5 in history, **When** they open `/my-loans`, **Then** they see 2 sections (active, history) + due_date highlighted when it is close to the deadline (≤ 3 days)
2. **Given** the Member has never borrowed, **When** they open `/my-loans`, **Then** they see an empty state + the CTA "Search books"
3. **Given** the Member is not logged in, **When** they open `/my-loans`, **Then** they are redirected to `/login` + a return URL

**FR refs covered:** FR-005 (loan history read), FR-010
**Function refs:** [[FN-Web-Member-Loans]], [[FN-API-Loan-List]]
**DS components used:** `Card`, `Badge`, `EmptyState`, `Pagination`
**Risks:** a lot of historical data → needs pagination + the index `loan(member_id, created_at desc)`

### US3 — Librarian overrides the loan limit (Priority: P3)

**As a** Librarian **I want** to override a member's loan limit in special cases (e.g. a lecturer borrowing 10 books for a research room) **so that** we can serve cases the normal business rule does not cover

**Independent Test:** Librarian + a Member with 5 active loans → check out the 6th → the "override" button appears → press it + enter a reason → the loan is created + the audit log records the override

**Acceptance Criteria:**

1. **Given** the Member has 5 active loans, **When** the Librarian presses checkout + presses override + enters a reason (≥ 10 chars), **Then** the loan is created + the audit log records `override_reason`
2. **Given** an override with no reason entered, **When** it is submitted, **Then** the system rejects it + shows an error
3. **Given** a Member-role login attempts the override endpoint, **When** the API is called, **Then** HTTP 403

**FR refs covered:** FR-001 (extended), FR-040 (audit override)
**Function refs:** [[FN-Web-Lib-Checkout-Override]], [[FN-API-Loan-Override]]
**DS components used:** `Modal`, `Textarea`, `Button` (danger variant)
**Risks:** abuse — a librarian overriding too often → add a weekly audit dashboard to the Admin view

## 9. Risks

- **R1** — race condition during checkout — mitigation: DB unique partial index `WHERE status = 'open'`
- **R2** — the barcode scanner emits characters faster than the UI debounce can keep up — mitigation: take the whole buffer before parsing, inside a 50 ms window
- **R3** — a Member with no email in the DB → checkout succeeds but the reminder cannot be sent — mitigation: warn in the UI + flag it in the audit
